# Every CSS property Chromium 141 reports on a computed style, with
# a value that a working implementation must visibly change the
# computed style for.
#
# A value here earns its place by being one Chromium itself computes
# differently from the property's initial value, checked by setting it
# on a probe and reading getComputedStyle back. A row that fails that
# check measures nothing: the property could be implemented perfectly
# and the row would still read as missing. A row may carry two
# declarations where one is not enough -- a border width needs a border
# style beside it or it computes to zero, and `resize` needs an
# `overflow` that is not `visible` or nothing it does is painted,
# though its computed value moves either way.
#
# A row is `property<TAB>value`. A third column declares the row
# ungradeable and says why. A FOURTH column names a pseudo-element, and
# then the declaration goes into a `#t::<pseudo>` rule rather than a
# style attribute and both the runner and the Chromium audit read the
# answer off that pseudo-element. A property whose whole effect is on
# `::first-letter` cannot register against the element's computed style
# however complete it is, because nothing it does reaches the element.
# Such a row needs a context declaration beside the property, because a
# pseudo-element with no declarations at all is not generated and there
# would be nothing to compare against.
#
# Only the first declaration in a row is the property under test; any
# that follow are context, and the row is graded against an element that
# already has them. Without that, `border-top-width: 10px; border-style:
# solid` registered on the strength of the `solid` alone, and would have
# gone on registering if width parsing were deleted outright.
#
# A value must differ from the initial value on every Chromium build,
# not just the one it was chosen against. A width of 3px does not:
# `medium` is 3px, so a build reporting the computed rather than the
# used width sees no difference, and `outline-width: 3px` passed here
# and failed in CI. The widths are 10px, which is neither 0 nor medium.
#
# A third tab-separated column marks a row this instrument cannot grade
# whatever value it carries, and says why. Those are excluded from the
# denominator and named by --verbose, rather than counted as properties
# this engine has not implemented.
#
# A value must also be one the style attribute can carry, because that
# is how both this file's grader and its audit deliver it. A CSS string
# written with double quotes ends the attribute early and arrives as
# nothing, and the property then computes its initial value -- which
# reads exactly like a property Chromium cannot tell apart. Three rows
# sat here excused as ungradeable for invented reasons on the strength
# of that, and all three grade perfectly once their strings are written
# with single quotes. The audit names this case separately now.
#
# The list is not Chromium's indexed enumeration of a computed style.
# That enumeration reports 406 names, of which 33 are `-webkit-`
# prefixed -- the CSS Snapshot does not define those and this engine
# deliberately drops them -- but it also omits 120 properties Chromium
# computes perfectly well and answers for through getPropertyValue.
# Eighty-one of those are shorthands and six are legacy aliases, neither
# of which belongs in a per-longhand instrument; the remaining 33 are
# ordinary longhands and are here. Seven of them -- `quotes`,
# `counter-increment`, `counter-reset`, `contain`, `content-visibility`,
# `text-decoration-thickness` and `text-underline-offset` -- this engine
# already implemented, and went uncounted for as long as the list was
# taken from the enumeration.
#
#     property <TAB> value
#
# A value may be several declarations where one alone cannot show the
# effect: border-*-width computes to zero while the border style is
# none, which is correct, so those rows set a style too.
#
# tests/conformance/properties.f sets each one on an element and
# compares that element's computed Style with the same element
# without it. A property that changes nothing is not implemented.
# The count is what css-2026.md's per-specification table is made of,
# and it may not go down (CLAUDE.md §2).
#
# 226 rows still read `initial`, which is a placeholder rather than a
# probe: `initial` computes to the initial value, so such a row can
# never register as implemented no matter what the engine gains. Those
# rows are all properties nothing here implements, so the count is
# correct today -- but before implementing a property, give its row a
# real value, or the number will not move when the work lands. The
# three flex rows that read `1` were exactly this trap.
