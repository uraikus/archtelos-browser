# CSS: what the style engine implements, against the 2026 snapshot

The target is the **[CSS Snapshot 2026](https://www.w3.org/TR/css-2026/)**
(CLAUDE.md, §2). The snapshot sorts specifications into four classes;
this file takes them in its order and states, for each, what the engine
does. The work it implies is in [todo.md](todo.md).

**The engine column is read from the code**, not from the other
documents: all of `src/css/`, plus the places `src/layout/layout.f` and
`src/paint/paint.f` consume a computed value. A property the cascade
computes but neither reads counts as absent, because a page renders the
same either way. Nothing is excluded by it now: `overflow` was, until
the painter began clipping by it.

`www.w3.org` is refused by this network's egress policy — the proxy's
CONNECT is answered 403 — so the snapshot has to be supplied to a
session rather than fetched, as it was for this one.

## The headline

The official definition of CSS is 24 specifications. **The engine
implements no part of 2 of them** and part of the other 22, two of those
completely — Namespaces 3 and Conditional 3. The two it does not touch
are the two it cannot: **Compositing and Blending 1** needs a
compositing operator, and the runtime sets `CAIRO_OPERATOR_SOURCE` at
every draw with no call to change it; **Easing 1** describes the timing
functions of transitions and animations, which need a clock and a
repaint loop rather than a property.

Of the three lower classes, Grid is substantially implemented, Selectors
4's functional pseudo-classes are, Fragmentation 3 has the break
controls a column context can act on, Masking 1 has `clip-path`, Shapes 1 has `shape-outside`, and Transforms 2 and Containment 2
have the parts that are not three-dimensional or dependent on knowing
what is on screen. `@layer` orders the cascade, and Color 5 is
both of its features.

Three runners in `tests/conformance/` put numbers on it, and each is a
floor the suite will not let drop:

| Measure | Now |
|---|---|
| CSS properties that change what renders, of the 405 the instrument can grade | **210** |
| HTML elements whose default `display` matches Chromium's, of 122 | **122** |
| CSS selectors matching the same elements as Chromium, of 61 | **61** |

The property count uses the same rule as this file: a property the
cascade computes but neither layout nor paint reads is not implemented,
because the page renders the same either way. `overflow` is what
still falls to it.

## 1. The official definition

Everything here is stable, and the snapshot's own framing is that this
is CSS "in its most complete form". The gaps in this table are the ones
that matter first.

| Specification | Engine |
|---|---|
| **CSS Level 2** | The bulk of what works: normal flow with margin collapsing, `overflow` in all of `visible`, `hidden`, `clip`, `scroll` and `auto` -- the last two reserving fifteen pixels inside the padding box for a scrollbar and painting one there, `scroll` always and `auto` only where the content overflows, which costs those boxes a second layout of their content. Such a box scrolls on both axes: the wheel over it moves its content down and a wheel tilted sideways moves it across where the window system reports one, either thumb can be taken hold of and dragged, and both follow the content -- the painter draws it from the same four functions the pointer is tested against, so where it looks and where it can be grabbed are one rectangle rather than two formulas that agree -- and hit testing adds the offset back so a link inside it is clickable where it looks. A horizontal `auto` bar is raised by a line of text too long to break as well as by a child box reaching past the edge, which is what Chromium does: a 100x60 box of one unbreakable word has a client height of 45 in both. The offset is kept by element id, because a box tree lasts one layout and a scroll position outlives several -- percentage heights resolved against a definite containing block and `auto` where there is none (§10.5), with `min-height` and `max-height` taking them the same way, inline formatting and line boxes, table layout (§17) in both algorithms — automatic, and the fixed one that takes its column widths from the first row and never measures a cell's content — with `caption-side` and `empty-cells`, list markers inside or outside the box, restyled by `::marker` -- a colour on it moves nothing, a `font-size` on it makes a marker as wide as one the item's own font size would have made, and a `content` replaces the label with its own string, which is where `content: counter(list-item)` belongs -- and **positioning** (§9.3) — `relative` offsets a box and its descendants without disturbing the flow, `absolute` and `fixed` leave the flow and resolve against the nearest positioned ancestor or the viewport, all four inset properties work, and `z-index` orders positioned siblings. **Floats** (§9.5) work too: a float is placed at the edge of its containing block after any float already there, the line boxes beside it are shortened so text wraps around it, a block box's own position and width ignore it, and `clear` moves a box below the floats on a side. A float with `width: auto` is shrink-to-fit — `min(max(min-content, available), max-content)` (§10.3.5) — so it hugs its content, and a single word wider than the space available makes it wider than its container rather than breaking the word. **Generated content** (§12) works: `::before` and `::after` generate boxes from `content`, which takes strings, `attr()`, `counter()`, `counters()` and the four quote keywords, and `counter-reset` and `counter-increment` maintain counters with the standard's scoping — an instance is in force for the element that reset it and that element's descendants, and for its following siblings as well unless an instance of the same name was already in scope, in which case it is the element's own subtree and no further. `quotes` gives the strings for `open-quote` and `close-quote`, at a depth that runs over the whole document in document order rather than following element nesting, repeating the last pair past the end of the list; `<q>` gets a pair from the user-agent stylesheet. `url()` in `content` generates a replaced box at the image's intrinsic size, in the order it was written among the strings beside it, and a url that does not load generates no box at all rather than a placeholder; a `width` on such a pseudo-element does not resize the image, and its margin, border and padding surround the whole run. On an **ordinary element** a `content` naming an image replaces the element's contents with it: the element becomes a replaced element sized by the ordinary rules from the image's natural size, keeping its own background, border and declared width and height, and its children are not rendered. A `content` holding anything but a `url()` replaces nothing there, which is what Chromium does with a string. A counter is always rendered in decimal. **`overflow: hidden`** clips a box's descendants to its padding box, painted through an offscreen image because the canvas has no clip region — and inside such a subtree a `border-radius` is drawn square, because an image has no path API (FINDINGS.md). `::first-letter` (§5.12.2) styles the first letter of a block's first line, taking preceding punctuation with it and skipping leading whitespace. `::first-line` (§5.12.1) styles the characters that end up on the first line, metrics included: the cascade computes, for the block and every inline inside it, the style it would have under the fictional element the standard describes, and the line's fragments and its strut are given those styles as the line is filled, so a first line set larger is taller and holds fewer words. Where a block's inline content sits in anonymous boxes -- beside block-level siblings -- the rule belongs to the first of them and to no other, which is what Chromium does. The restricted property set the standard defines for the pseudo-element is not enforced. `clip` (§11.1.2) cuts an absolutely positioned box to a rectangle, through the same machinery as `clip-path`. `orphans` and `widows` (§13.3.1) constrain where a paragraph may be broken; there are no pages here, so they act where the only fragmented context is, between the columns of a multi-column container. **Paged media** (§13) works: `@page` declares the page box, with `size` in the ten named sheets -- A5 to A3, B5, B4, the two JIS sizes, letter, legal and ledger -- or one or two lengths, turned by `portrait` and `landscape`, and `margin` in the one-to-four-value form with percentages of the page box. `@page :first`, `:left` and `:right` declare it for particular pages, the first page being a right-hand one, and a named `@page` for the pages a `page` property sends there; the selectors are weighed as the triple Paged Media 3 §3.5 gives, so `:first` outranks `:right` however they are ordered, and rules accumulate rather than replace one another. `size: auto` is US Letter, which is the sheet Chromium prints on beside it. A page is a fragmentation container like a column, so pagination is the column algorithm over a different one: the same units, the same rules about where a break is allowed, and the same search for the nearest allowed point -- with the height asked for one page at a time, because `@page :first` can make the first sheet a different size from the rest. CSS2's `page-break-before`, `page-break-after` and `page-break-inside` are the three fragmentation properties under their older names (Fragmentation 3 §4.4), so they are renamed where a declaration is applied rather than implemented again, which makes the cascade between an old spelling and a new one one property's cascade. A change of `page` between two siblings forces a break into the named run and out of it again. A box taller than the sheet is cut at the page's edge rather than left to run off it. `--print` writes one image per page, and `@media print` is the medium such a render answers to, so a document's print stylesheet is the one that applies to its pages. Three parts are missing: the margin boxes (`@top-center` and its siblings) are parsed and dropped, the side a `break-before: left` asks for is not honoured because honouring it means generating a blank page, and a named page cannot take a different `size` from the first, because the document is laid out once at the first page's width. A margin that collapses all the way through to the root is dropped rather than moving the document down |
| **CSS Syntax 3** | Partial, and not by this algorithm. There is no tokenizer in the standard's sense: parsing is index scanning. Comment stripping runs first and is not string-aware, so `/*` inside a string or `url()` opens a comment. Escapes are accepted in identifiers and never decoded, so `.a\.b` can never match. No `<!--`/`-->` |
| **CSS Style Attributes** | Yes. The `style` attribute is parsed per element, though it is treated as an origin above author rules rather than as a specificity |
| **Media Queries 3** | Every feature the level defines, in the boolean form as well as with a value: `width`, `height`, `device-width`, `device-height` and their `min-` and `max-` forms; `orientation`; `aspect-ratio` and `device-aspect-ratio`, compared as two whole numbers rather than two divisions, so 800 by 600 is `4/3` exactly; `color`, `color-index` and `monochrome`, which say eight bits a component, no colour table and not monochrome; `resolution` in `dpi`, `dpcm`, `dppx` and `x`, which says 96 to the inch; and `grid` and `scan`, which describe devices this is not. What it calls the device is its own window: there are no screen metrics to ask for, and a page asking about the device is deciding whether it is on a phone, which the window size answers as well as the screen does. `hover` and `pointer` answer `hover` and `fine`, because this browser opens a window with a pointer in it — headless Chromium answers `none`, which is a fact about that process rather than about the standard. The remaining gap is time rather than features: a query is evaluated when the sheet is parsed, so resizing the window does not re-evaluate it |
| **CSS Conditional 3** | Both. `@supports` evaluates its condition: a declaration is supported when the property is one the cascade computes and the value uses no function the engine cannot resolve. `not`, `and`, `or` and nesting are handled; `selector()` reports unsupported. The list of properties it answers from is checked against the property instrument on every run: a property that changes what renders and is not on the list, or is on the list and changes nothing, fails the suite, because a hand-written list beside a measurement drifts from it in both directions and silently |
| **Selectors 3** | Every selector this can measure, it gets right: all 61 entries in `tests/conformance/css-selectors.txt` match exactly the elements Chromium matches. Type, `*`, `#id`, `.class`, all six attribute operators, all four combinators, the full `An+B` grammar in `:nth-child()`, `:nth-last-child()`, `:nth-of-type()` and `:nth-last-of-type()`, the `first`/`last`/`only` child and of-type pseudo-classes, `:root`, `:empty`, `:link`, `:enabled`, `:disabled`, `:checked`, `:lang()`, and `:not()` with one compound. A rule whose selector list contains anything unparseable is dropped whole, as §4 requires. `:target` parses and matches nothing, which is right for a document never navigated to a fragment. **`::before`, `::after`, `::first-letter` and `::first-line` all work**, in both the one- and two-colon spellings, and **`::marker`** works in the two-colon spelling the standard gives it -- `:marker` with one colon is not a pseudo-element, so it matches nothing |
| **CSS Namespaces 3** | All of it. `@namespace` binds a prefix, or a default namespace when it names none, and a selector's namespace part is honoured: `ns|E` for a declared prefix, `*|E` for any namespace, `|E` for no namespace, and a bare `E` for any namespace until a default is declared and then only that one. A prefix nobody declared makes the selector invalid, so it matches nothing rather than being read as a type. Every element in an HTML document is in the XHTML namespace, so all of this comes down to one string comparison — which is also why the whole specification can be honoured rather than approximated |
| **CSS Cascade 4** | Substantially. Specificity is the triple (ids, classes and attributes and pseudo-classes, types), packed base 1024 so that an integer comparison is the lexicographic one. Importance inverts the origin order, so an important user-agent declaration outranks an important author one. `inherit` takes the parent's computed value, `initial` the initial value, and `unset` whichever of the two the property calls for. **`revert` rolls the property back to the value the previous origin gave it**: the matches arrive sorted, so the user-agent origin's declarations are the ones before the first weight at or above the origin boundary, and copying the map there is the whole of the bookkeeping -- done only on a page that says `revert` at all. A rollback that finds nothing in that origin is `unset`, which is what removing the declaration leaves. **`revert-layer`** rolls back one step rather than the whole origin: the matches carry the origin and the layer packed into one rank, so a change in that rank is a layer boundary, and the map as it stood before each layer began is what the keyword resolves against. An unlayered declaration is in the implicit outer layer, which comes after every named one, so reverting one of those lands on the last named layer -- green where `revert` beside it lands on black, which is Chromium's answer too. A style attribute ranks above an unlayered rule, so `revert-layer` there rolls back to that rule and `revert` past it to the user-agent sheet: 400 and 700 on the same `<b>`. Resolving after the declarations are applied rather than at each one is what makes a shorthand work, because `applyDecl` has expanded it into longhands by then. `all` sets every property at once: it drops every declaration before it in the block, and for `initial` computes the element as though it had no parent, which is what every default in the cascade already means by "root"; `all: revert` puts the previous origin's declarations back, `all: revert-layer` the previous layer's, and `unset` needs nothing beyond the dropping. `direction` and `unicode-bidi` are left alone, as the standard says. A CSS-wide keyword is a valid value for every property, so `display` -- the one property validated where it is applied, because by then the declaration it beat is gone -- lets one through, and `display: inherit` takes the parent's. Missing: `all: inherit`, which would have to give a *non-inherited* property the parent's value and so needs the parent style copied field by field |
| **CSS Values and Units 3** | Partial. Units: unitless, `px`, `%`, `em`, `rem`, `pt`, `pc`, `in`, `cm`, `mm`, `q`, `ex`, `ch`, `cap`, `ic`, `vw`, `vh`, `vmin`, `vmax`, and from Values and Units 4 `lh` and `rlh`, the `vi` and `vb` axes, and the small, large and dynamic viewport units, which are three names for this viewport because nothing here slides away to tell them apart. `ex` and `ch` are half an em and `cap` three quarters of one, the runtime reporting neither an x-height nor a zero's advance nor a cap height; `ic` is an em, which is what it is in every font this engine can load. Angles are read wherever one is taken -- a gradient's direction, `rotate()` -- in `deg`, `grad`, `rad` and `turn`. `lh` is the element's own computed line height and `rlh` the root element's: the cascade computes `line-height` before every other length, so the unit reads it off a global that is already set -- and that still holds the *parent's* while `line-height` itself is being computed, which is what the unit means there, the way `em` inside `font-size` means the parent's font size. Under `line-height: normal` it is what a line box actually comes out at, 1.2 times the font size, which is 19px at 16px in this engine and in Chromium alike. Missing: the time and frequency units, which belong to the animations this engine does not run. Resolutions are read in a media query, in `dpi`, `dpcm` and `dppx`. `calc()` is implemented: a sum of products over lengths and plain numbers, with nested parentheses and nested `calc()`, and a result that carries a pixel part and a percentage part separately so `calc(100% - 2em)` waits for the containing block. The standard's invalid cases are rejected, among them a `-` without spaces around it and a length added to a number. `attr()` is missing. `rem` multiplies the root element's computed font size and `vh` the real viewport height |
| **CSS Custom Properties 1** | Yes. Custom properties are kept, inherit, and `var(--name, fallback)` substitutes them wherever a value is read, including inside another custom property. An unresolvable `var()` with no fallback makes the declaration invalid rather than empty, as the standard requires. A vendor prefix is still dropped |
| **CSS Box Model 3** | Yes, in substance: all four margins and paddings, and margin collapsing, which CSS2 §8.3.1 still owns |
| **CSS Color 4** | Substantially: `transparent`, `currentcolor`, all four hex forms, `rgb()`, `rgba()`, `hsl()`, `hsla()` with either separator and alpha, all 148 named colors, all nineteen system colors, `opacity`, and the wider color spaces — `hwb()`, `lab()`, `lch()`, `oklab()`, `oklch()` and `color()` over `srgb`, `srgb-linear`, `display-p3`, `a98-rgb`, `prophoto-rgb`, `rec2020`, `xyz`, `xyz-d65` and `xyz-d50` — each with `none` components, percentages on the standard's own scales, a hue in degrees, radians, gradians or turns, and a slash alpha. They resolve to a packed sRGB integer through the standard's conversion matrices, clamped per channel where the color falls outside the sRGB gamut rather than gamut-mapped, which is what Chromium paints for these colors too. No `<color>` interpolation, since nothing here animates. `opacity` is not inherited: its computed value is the element's own, and a separate accumulated value carries group opacity to the painter, which approximates it rather than compositing a layer. The color syntax is graded by tests/unit/test_color4.f, whose expected pixels were derived twice over — from the standard's §17 pseudocode in a separate script, and from the pixel headless Chromium paints — because the property instrument counts `color` as implemented whatever syntax reaches it |
| **CSS Backgrounds and Borders 3** | Partial: `background-color`, a `background-image` from `url()` or a gradient, `background-repeat` in all five forms, `background-position` with keywords, lengths and percentages on both axes, and `background-position-x` and `background-position-y`, which the shorthand expands into so that the later of the two wins whichever way round they are written, `background-size` with `cover`, `contain`, lengths, percentages and `auto`, and `background-origin` and `background-clip` over all three box edges, per-side border width, style and color, the `border` shorthands, and `border-radius`. A background image is fetched after the cascade, since the URL only exists once styles are computed, and a tile that runs off the box is cut off there. A tile drawn at a size other than the image's own is scaled once and blitted from, with the image padded from the edge the next tile will be -- the opposite edge on an axis it repeats along, its own edge on one it does not -- because a scaled blit fades at its own edges and a row of them would show the box between one tile and the next. every border style paints as itself, per side: `solid`, `dashed`, `dotted`, `double` — whose two lines and gap are each as near a third of the width as it allows — and `groove`, `ridge`, `inset` and `outset`, which shade an edge against its opposite, the two shades being the border colour and half its brightness, since the standard fixes only that they are based on it. `border-radius` sets each corner separately — the shorthand's one to four values, the four `border-*-radius` longhands and the four logical corner names — in lengths or percentages, a percentage of the box's width for a horizontal radius and of its height for a vertical one, and each corner may be an ellipse rather than a quarter circle: the `/` form gives the horizontal radii before the slash and the vertical after, and a longhand takes the pair directly. Where two radii on one edge would overlap, every radius is divided by the same factor until they do not (§5.5), so `border-radius: 60px` on a 40px box is `20px` and keeps its shape. `box-shadow` casts outer and `inset` shadows with offset, blur, spread and a list of shadows. The canvas has no blur, so an outer shadow's is computed rather than filtered: a Gaussian blur of a rectangle has a closed form, one axis's alpha being the difference of the Gaussian's own integral at the two edges and the whole of it the two axes multiplied, which puts half the colour against the shadow's edge and a quarter of it diagonally past a corner (§7.1). The standard deviation is half the blur radius and the integral is Abramowitz and Stegun 7.1.26, whose error is a thousandth of what a painted pixel can show. The corners are the one part where both axes vary, and they are drawn a row at a time by blitting one axis's profile at the other axis's share, because `drawImage` multiplies an image's alpha by `fillAlpha` and a separable blur is a product. The shape a shadow is cast from is the border box's, corner radii and all, grown by the spread, with a round corner growing by it and a square one staying square (§6.2). A rounded rectangle's blur does not separate, because the shape's width changes with the row, but the outer integral still holds: the value at a point is the sum, over the rows the shape covers, of that row's share of the vertical Gaussian times the horizontal Gaussian over that row's own span, which telescopes back into the product of the two axes when every radius is zero -- so the two ways of reaching a pixel have to agree where a radius cannot reach, and the suite asks them to, at the middle of an edge. Only the corners need the sum, over bands widened to hold the radius as well as the blur's reach, because past a corner's band every row is the full width again; the edges and the middle stay the single fills they were, and a shadow whose box has no radius resolves no radii and paints what it painted before. A row an ellipse crosses is taken in eight slices rather than at its middle, because the edge of a circle goes as the square root of the distance from the top of it and the midpoint of such a row is too wide, which biases the axis the rows run across and shows up as a circle casting a darker shadow above itself than beside itself. Measured against a reference of 64 slices, the worst case over a 40x40 circle at blurs of 4, 8 and 20, a 100x100 at 8, a 30x30 at 2 and a 200x80 at 30 is 3.7 units of 255 at one slice to the row and 0.77 at eight. Against Chromium the profile agrees in shape and runs two or three units lighter throughout, which is the gap the square corners already carry between a true Gaussian and the three box blurs Skia approximates one with. An `inset` shadow's blur is the same Gaussian from the other side: the inside of the shadow is the outside of its hole, so its alpha is one minus the two axes multiplied, which is what a pass at `1 - fx` and a pass at `1 - fy` accumulate to -- two sets of plain strips, with no per-pixel work at all. Two passes only compose to that at full alpha, so a shadow that is not opaque is painted into an image at full alpha and blitted at the alpha it asked for, which is also what keeps the strips inside the padding box. `border-image` cuts its source into nine regions by `border-image-slice`, which takes a number or a percentage on each side and `fill` for the middle: the four corners are drawn at the border's own size, the four edges fill what the corners leave, and `border-image-width` and `border-image-outset` move and resize the area they go in. §6.5 scales every edge image to the thickness of the border it fills -- the top edge vertically to the top border width, and horizontally by the same factor -- before any tiling, so a 3px slice in a 30px border tiles at 30px; the middle takes the top edge's factor across and the left edge's down, falling back to the opposite edge's where one of them has nothing to scale by. `border-image-repeat` then says how those tiles fill the edge, in all four values and in both of its two, one for the horizontal edges and one for the vertical: `stretch` pulls one tile across the edge, `repeat` centres whole tiles on it and lets its two ends cut a tile each, `round` resizes the tile until a whole number of them fills the edge exactly, and `space` lays down only whole tiles and shares what is left over into gaps around them -- one before the first, one after the last and one between each pair -- drawing nothing at all where not even one tile fits. A scaled blit samples half a source pixel past the rectangle it fills and fades to transparent where there is nothing there, which showed the page through a five pixel seam between one tile and the next, so each region is padded with a copy of its own edge pixels and scaled with that padding outside the tile, and every tile of one size is that one image blitted unscaled. Each region is cut by blitting the source into a blank image at a negative offset, because an image destination has no source-rectangle `drawImage` (FINDINGS.md) and a border image inside a clipped subtree is painting into one. `background-attachment: fixed` positions the image against the viewport rather than the element, so it stays put while the page scrolls under it, clipped to the element as always; it says nothing about a background colour, which fills its box either way. Several layers per box: `background-image` takes a comma-separated list and every other background longhand takes one too, the i-th value going with the i-th image and a shorter list repeating from its start. The layers paint back to front in the reverse of the order they are written, so the first written is on top, and the colour goes underneath them all, clipped by the last layer's `background-clip` as the standard says. A clipped background keeps the border box's `border-radius` rather than deriving the smaller inner curve |
| **CSS Images 3** | All of it bar one fallback, named at the end of this row: `linear-gradient()`, `radial-gradient()`, `conic-gradient()` and all three repeating forms as a background image. A linear gradient takes `to <side>` and `to <corner>` keywords and an angle in `deg`, `turn`, `rad` or `grad`; a radial one takes `circle` and `ellipse`, all four extent keywords, explicit radii and `at <position>`, and a degenerate ending shape renders as the last stop, except the one with zero height and a width of its own, which renders as the linear gradient mirrored about its centre that the standard names; a conic one takes `from <angle>` and `at <position>`, and its stops are positioned by angle or by a percentage of the turn, which say the same thing.  All three take any number of colour stops, positioned in percentages, lengths or angles, or omitted and spaced evenly, with interpolation hints between them -- a bare position saying where the colour is halfway between its neighbours, the ramp either side following the standard's `P ^ (log 0.5 / log H)` curve -- and all three are painted as flat bands -- parallel, concentric or wedges -- rather than by the canvas's own gradient, which cannot be called with colours that are not literals (FINDINGS.md, "a gradient cannot be built at run time"). A wedge's span on a row is computed from the tangent of its edges rather than searched for, so a conic sweep costs about what an off-axis linear one does: 12 ms against 14 for the same sixty boxes (benchmarks.md). `object-fit` in all five values and `object-position` with keywords and lengths on both axes, sized by the specification's own algorithm and clipped to the content box. `object-view-box` (Images 4) names a rectangle over a replaced element's own pixels which becomes its natural size, in all three spellings — `inset()`, `rect()` and `xywh()` — with percentages of the image's size; `object-fit` then fits that rectangle rather than the whole image. A view box reaching outside the image, which a negative inset asks for, is empty there rather than repeating an edge, because the region is cut by blitting into a blank image and what falls outside is never drawn. **`image-set()`** chooses among candidates by resolution: the smallest at or above this display's, and the largest below it when there is none, so a list of only 2x and 3x still paints. A candidate is a `url()` or a bare string, a resolution in `x`, `dppx`, `dpi` or `dpcm` -- 96dpi is 1dppx, as Chromium computes it -- and a `type()` that says what the file is rather than how big; a candidate naming no resolution is 1x. This display is one device pixel to the CSS pixel, which is also what `resolution` answers in a media query. **`image()`** takes its source the same two ways; the colour it can name to fall back on when that source does not load would be a solid-colour image, which nothing here can make, so it is read and dropped. **`cross-fade()`** mixes two images by weight, the second blitted over the first at its own share -- which for two opaque images is exactly the standard's mix, because the first is already down at full alpha. Chromium implements only `-webkit-cross-fade(A, B, p)`, and its pixels say (1 - p) of A plus p of B byte for byte; this engine agrees with them everywhere except where a channel lands on exactly half of 255, which Chromium rounds up and Cairo down: half and half of blue and red is #800080 there and #80007f here, one unit in one channel |
| **CSS Fonts 3** | Partial: `font-family`, `font-size` with the absolute and relative keywords, `font-style`, the `font` shorthand, and `font-weight` **as a boolean**. The rest of this level is the intrinsic sizing keywords, which are Box Sizing 3's gap as well |
| CSS Positioned Layout 3 | CSS2's positioning is implemented (above), and the `inset` shorthand with its block and inline forms. Nothing else this level adds: no stacking contexts beyond painting positioned siblings in z-index order, and no `sticky` behaviour — it computes as `relative` |
| Selectors 4 | The five the measurement used to fail, which were all from here: `:is()` and `:where()`, which differ only in that `:where()` contributes no specificity; `:has()`, as a descendant test; a selector list inside `:not()`; and the attribute case-sensitivity flag. `:has()` with a leading combinator — `:has(> p)` — names a relation this engine does not distinguish and is refused rather than read as a descendant test. Nothing else from this level |
| CSS Color 5 | `color-mix()` over every interpolation space the standard names: the rectangular `srgb`, `srgb-linear`, `xyz`, `xyz-d65`, `xyz-d50`, `lab` and `oklab`, and the polar `hsl`, `hwb`, `lch` and `oklch` with all four hue-interpolation methods. Mixing is premultiplied, so a transparent colour contributes its alpha and nothing else, and percentages that do not add to a hundred are normalised with what they came to carried into the result's alpha. Each space needed the conversion the wider colour spaces did not — sRGB *into* it rather than out of it — which is what made the polar spaces possible. The **relative colour syntax** came of the same conversions: `rgb(from <color> r g b)` and its form in every other colour function, with the origin colour's channels bound to the names that function writes them with, `calc()` over them, percentages on each function's own scale, and `none`. `color(from <color> <space> ...)` takes all eight predefined spaces, which needed the XYZ-to-linear matrices for the four wide RGB ones — the inverses of what the absolute forms use, and what the identity check proves right |
| CSS Transforms 2 | The individual `translate`, `rotate` and `scale` properties, which this level adds; nothing three-dimensional |
| CSS Containment 2 | `content-visibility: hidden`, which skips an element's contents and carries size containment with it. No `content-visibility: auto`, which needs to know what is on screen |
| CSS Nesting 1 | A style rule inside a style rule, and the `&` that stands for the rule it is in: `&` anywhere in the nested selector, a nested selector with none, which gets one in front as a descendant, and a leading `>`, `+` or `~`, which gets one before the combinator. Nesting nests, and so do `@media`, `@supports` and `@layer`, in both directions: a style rule inside a nested at-rule, and declarations directly inside one, which belong to the rule the at-rule is in. A declaration written after a nested rule cascades after it, so a rule's declarations are emitted as the runs they are written in rather than gathered into one. A nested rule expands to the cross product of its own selector list with its parent's, up to 256 selectors; `&` in it weighs the most specific selector of the parent list, whichever branch a match came through, which is a correction applied to each expansion rather than a property of its text. An `&` inside `:is()` or `:not()` is refused rather than substituted, because those take a compound selector here and a parent may be a complex one. Nesting is syntax rather than a property, so the property instrument cannot grade it whatever it does; `tests/unit/test_nesting.f` does, against what Chromium computes off the same stylesheet and the same document |
| CSS Filter Effects 1 | **Nothing, and blocked on the language rather than on the work.** A filter is a function over the pixels an element and its descendants painted; this browser already paints a subtree into an image, which is how `clip-path` and `overflow: hidden` work, and `img.drawPixel` writes one back. What it cannot do is read one: `img.getPixelColor` returns a `color`, and a `color` supports equality and nothing else — no channel accessor, no packed form, and no ordering to search with (FINDINGS.md, finding 35). The specification's matrices have been derived and checked against Chromium on twenty-seven cases and are kept in todo.md, so the implementation is one accessor away. `blur()` and `drop-shadow()` are a separate question and stay out regardless: one is a convolution, the other wants the path API an image does not have |
| CSS Transitions 1, Animations 1, Motion Path 1, Will Change 1, Fonts 4, Scroll Anchoring 1 | Nothing. `@keyframes` blocks are skipped, and nothing here would run them: an animation needs a clock and a repaint loop, which is an addition to the browser shell rather than a property |
| CSSOM, CSSOM View, Geometry 1, Font Loading 3, Web Animations 1, Resize Observer 1 | Out of scope permanently: these are script interfaces, and there is no JavaScript engine (todo.md, "Deliberate non-work") |

## What this changes about the plan

**The snapshot's classification and this project's priorities do not
agree, and the classification wins on two counts.** Custom properties
with `calc()`, flexbox, and CSS Images are in the official definition of
CSS, not in some forward-looking tier: an engine missing them is missing
stable CSS, not modern CSS. Conversely `:is()`, `:where()`, `:has()` and
`@layer` ordering sit in the two lowest classes, so they are further
down the list than their prominence suggests.

**Positioning is official-definition work too**, through CSS2 §9.3
rather than through Positioned Layout 3. So are floats, `overflow`
clipping and generated content. The four largest holes in the engine are
all CSS2 chapters.

**The cascade bugs are fixed.** Specificity is compared as a triple,
importance inverts the origin order, `inherit` takes the parent's value,
`@supports` evaluates its condition, `text-decoration` and `opacity` no
longer inherit, `rem` and `vh` resolve against the real root font size
and viewport, and an unparseable selector drops its whole rule. What
remains of Cascade 4 is `revert` and `all`.

**A corpus is still the missing instrument.** The HTML parser went from
20% to 93% because someone else's tests said what was wrong; `css/` in
web-platform-tests is the equivalent, and the open question is how much
of it runs without script.
